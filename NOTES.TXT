7. FILE HASH
============================================================

The ingestion code calculates SHA256:

calculate_file_hash(file_path)

Purpose:
Identify the actual contents of a file.

Example:

customers.csv
SHA256 = ABC123

Tomorrow:

customers.csv
SHA256 = ABC123

Result:
Same file content -> SKIP


Tomorrow:

customers.csv
SHA256 = XYZ789

Result:
Same filename but different content -> LOAD


IMPORTANT:

Filename is NOT the identity.

Filename + content hash is the identity/version.

============================================================
38. WHY WE DO NOT ALWAYS USE --force
============================================================

Normal production:

python -m src.ingestion.bronze_ingestion customer

The program calculates:

SHA256(file)

Then checks:

SOURCE_NAME
+
FILE_NAME
+
FILE_HASH

If that exact file version already succeeded:

SKIP


If the filename is same but hash changed:

LOAD


This prevents:

customer.csv
customer.csv
customer.csv
customer.csv

from accidentally loading the same data repeatedly.


--force means:

"I KNOW this file was already processed,
but intentionally load it again."


Therefore:

--force = exception/testing/recovery

NOT:

--force = normal ingestion


============================================================
39. RECOMMENDED REAL-WORLD FILE VERSION LOGIC
============================================================

File arrives:

customers.csv
Hash A

Log:

customer | customers.csv | Hash A | SUCCESS


Same file arrives again:

customers.csv
Hash A

Result:

SKIP


New contents arrive:

customers.csv
Hash B

Log:

customer | customers.csv | Hash B | SUCCESS


Now history contains:

customers.csv | Hash A
customers.csv | Hash B


This is why INGESTION_FILE_LOG must allow
multiple hashes for the same filename.


The current PRIMARY KEY:

SOURCE_NAME + FILE_NAME

is NOT sufficient for this requirement.


It must be redesigned to support:

SOURCE_NAME + FILE_NAME + FILE_HASH

or another version/surrogate key.
